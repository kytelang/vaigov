# Kyte TLS stack — end-to-end interop diagnosis (2026-10-12)

Empirical audit of all four quadrants using openssl 3.6.4 as the known-good peer,
a captured real Chrome ClientHello, curl with a trusted anchor, and a Kyte client
test program. Evidence is reproducible.

## Summary table

| Quadrant | Transport handshake | Cert handling | Verdict |
|---|---|---|---|
| **Server TLS 1.3** | interoperable (openssl full handshake; curl full validation) | was serving a bad cert | FIXED (cert) + improved (HRR, ALPN) |
| **Server TLS 1.2** | not supported | n/a | GAP: 1.3-only |
| **Client TLS 1.3** | interoperable (openssl + cloudflare, unverified) | verification BROKEN | P0 BUG |
| **Client TLS 1.2** | only via the mTLS variant | shares the broken verifier | GAP + P0 BUG |

## 1. Server TLS 1.3 — the "never worked in a browser" bug was the CERTIFICATE

The TLS 1.3 server transport is interoperable:
- `openssl s_client -tls1_3` completes a full handshake (reads cert, derives keys,
  verifies server Finished) over X25519 and P-256.
- Replaying a real Chrome ClientHello, the server emits a valid ServerHello
  (correct `legacy_session_id` echo, x25519 key_share, `supported_versions=0x0304`)
  and the server parses Chrome's x25519 key byte-exact (verified via instrumented
  dump: MATCH).
- `curl --cacert dev-cert.pem` (full hostname + EKU + validity validation) →
  `ssl_verify=0`.

The browser failure (`ERR_SSL_PROTOCOL_ERROR` in Chrome/Brave, same in Safari) was
**not** the TLS stack. The dev certificate was generated by `openssl req -x509`
with no extensions, which defaults to **`basicConstraints: CA:TRUE` and no
`extendedKeyUsage`** — i.e. a CA cert, not a server leaf. openssl s_client accepts
it; every browser hard-rejects a CA/`!serverAuth` cert as a server certificate at
the TLS layer (no "proceed" bypass). **Fixed** by regenerating a proper leaf:
`CA:FALSE`, `keyUsage=digitalSignature`, `extendedKeyUsage=serverAuth`,
`subjectAltName=DNS:localhost,IP:127.0.0.1`, ≤398 days. `openssl verify -purpose
sslserver` now returns OK.

Two genuine robustness gaps were also found and fixed along the way:
- **HTTP/2-over-TLS response stall.** With ALPN negotiating `h2`, the server opens
  the stream but never returns a response (HTTP/1.1 is fine). Added an app-level
  `App.useHttp1Only()` / `tlsAlpn` knob (default unchanged) and the control plane
  now serves HTTP/1.1 over TLS. The underlying h2-over-TLS defect remains OPEN.
- **No HelloRetryRequest for post-quantum key_share.** When a client's only usable
  key_share was an unsupported group (Chrome's `X25519MLKEM768`), the server emitted
  a mismatched key_share. Added a spec-correct HRR (RFC 8446 §4.4.1 `message_hash`
  transcript) that falls back to X25519. Verified against openssl.

## 2. Server TLS 1.2 — NOT SUPPORTED (1.3-only)

A `-tls1_2` ClientHello to the server fails (`Cipher is (NONE)`, no certificate);
1.0/1.1 are refused. The web `App` accept path (`net.asynctls.tlsAcceptAlpn` ->
`net.tlsmembio` ServerBio) only wires the TLS 1.3 engine. A `crypto/tls/12`
implementation exists in std but is not used server-side. Acceptable for browsers
(all do 1.3); a gap for legacy/non-1.3 clients.

## 3. Client TLS 1.3 — transport works, CERTIFICATE VERIFICATION IS BROKEN (P0)

Kyte client test (`web.client.Http`) results:

| Call | Result |
|---|---|
| UNVERIFIED `get` -> local openssl 1.3 | 200, full body |
| UNVERIFIED `get` -> cloudflare (real 1.3) | 200, 1.33 MB body |
| **VERIFIED `getVerified` -> local openssl 1.3** (dev cert as CA) | **"TLS handshake failed"** |
| **VERIFIED `getVerified` -> cloudflare** (system CA bundle) | **"TLS handshake failed"** |

- The client handshake, record layer, and HTTP all interoperate with real-world
  TLS 1.3 — but only on the **unverified** path.
- Certificate verification fails valid chains. The trust store parses correctly
  (`truststore.loadPemBundle`: dev cert -> 1 anchor, system bundle -> 128 anchors),
  so the defect is in **`crypto.x509.verifyCertList` / `verifyChain2` / `verifyChain3`**:
  it rejects both a self-signed EC leaf (verifyChain2, leaf == root) and cloudflare's
  real RSA chain against 128 system roots (verifyChain3).
- Structural limit: `verifyCertList` only handles a 2-cert (leaf->root) or 3-cert
  (leaf->one-intermediate->root) chain; chains with two intermediates can't verify
  even once the signature bug is fixed.

**Security impact:** the only working client path is unverified (no cert
validation). `entra-client` and the other `web.client` callers use
`Http.request(...)`, which is the unverified path — so outbound calls to
`login.microsoftonline.com` etc. currently do a TLS handshake with **no certificate
verification** (MITM-exposed). `getVerified`/`postVerified` (the secure API) is
non-functional.

## 4. Client TLS 1.2 — only via the mTLS variant; shares the broken verifier

The default client (`tlsConnect`/`getVerified`) uses the TLS 1.3 bio. The TLS 1.2
client (`net.tls12bio` + `crypto.tls.12.client12`) is only reached through the
client-certificate variant (`tlsConnectClientCert*`). Normal verified/unverified
1.2 client use is not wired, and verified 1.2 would fail on the same broken x509
verifier.

## Prioritised fixes

1. **P0 — fix the client x509 chain verifier** (`verifyChain2`/`verifyChain3` in
   `crypto/x509.ky`) so `getVerified` validates real chains (self-signed EC leaf +
   CA-rooted RSA/EC), then switch `entra-client` and `web.client` default calls to
   the verified path. This is the real security blocker for the Entra integration.
2. **P1 — multi-intermediate chain support** in `verifyCertList` (loop issuers,
   not a fixed leaf/inter/root shape).
3. **P1 — server TLS 1.2 accept** (optional; wire `crypto/tls/12` into the App
   accept path) if non-1.3 clients must be supported.
4. **OPEN — HTTP/2-over-TLS response stall** (worked around with HTTP/1.1-only).
5. **DONE** — server leaf cert; HelloRetryRequest for PQ key_shares; ALPN/h2 knob.

## UPDATE 2026-10-12 — fixes applied (verified)

Empirically verified with openssl, a real browser ClientHello, and a Kyte client
test against openssl-s_server, cloudflare, and the live Microsoft Entra endpoint.

**Fixed:**
1. **Server leaf certificate** — regenerated as a proper server cert (`CA:FALSE`,
   `serverAuth` EKU, `digitalSignature`, SAN, ≤398 days). Browsers now show only
   the normal self-signed warning, not a protocol error.
2. **Client x509 chain verifier** (`crypto/x509.ky`) — replaced the fixed
   leaf+1-intermediate `verifyChain2/3` with a general `chainTo` walker: parses
   every sent intermediate, walks `leaf → inter* → trusted anchor` with per-hop
   signature/validity checks, requires intermediates to be CAs, and applies
   trust-anchor semantics (the anchor need not carry `CA:TRUE`, so a self-signed
   leaf pinned as its own anchor verifies). Multi-intermediate chains now work.
   - Verified: self-signed EC leaf → 200; a wrong CA → correctly rejected.
3. **OCSP soft-fail** (`crypto/tls/truststore.ky`) — `trustsNotRevoked{,12}` now
   reject only a definitive `REV_REVOKED`; a stapled response that can't be fully
   validated (`REV_UNKNOWN`) is ignored, as every mainstream client does. This
   was the real blocker for Microsoft Entra (it staples OCSP).
   - Verified: `getVerified` against the live Entra OIDC endpoint → **200**, full
     body, with the system CA bundle; wrong CA still rejected.
4. **HelloRetryRequest for post-quantum key_share** (server) — Chrome's
   `X25519MLKEM768` falls back to X25519 instead of erroring.
5. **ALPN/HTTP-1.1 knob** (`App.useHttp1Only`) — avoids the h2-over-TLS stall.

**Net:** server TLS 1.3 and client TLS 1.3 now interoperate with real browsers and
real servers, and `getVerified` works against real RSA CA chains (Microsoft Entra)
— the control-plane ↔ Entra path can be made cert-verifying.

**Still open (do not block varman/Entra):**
- **P-384 ECDSA verification** — the client cannot verify a chain rooted at a
  P-384 CA (e.g. Google GTS R4 → cloudflare), because `crypto/ecc/p384.ky`
  exposes only ECDH, not ECDSA-verify (needs point-add + mod-n inverse). All-RSA
  and P-256 chains (incl. Entra) are fine.
- **Server TLS 1.2 accept** — server is 1.3-only (fine for browsers).
- **h2-over-TLS response stall** — worked around with HTTP/1.1-only.
- **Verified client with custom request headers** — `getVerified`/`postVerified`
  work; a general `requestVerified(method,url,headers,body,ca)` is not yet
  exposed, so `entra-client` still calls the unverified `request()`. Wiring it to
  a verified call is a small follow-up now that verification works.

## UPDATE 2026-10-12 (part 2) — the ACTUAL browser root cause

The earlier "browsers just don't trust the self-signed cert" conclusion was only
half the story and was wrong as the primary cause. The decisive experiment:
point the browser at a **Python `ssl` (OpenSSL) server using the same cert** and
at the Kyte server, in the same browser, with the mkcert CA trusted. The OpenSSL
server **loaded**; Kyte **did not**. That isolates a real Kyte defect that only
strict (browser) TLS stacks expose.

**Root cause:** Kyte's TLS 1.3 server emitted a `record_size_limit` extension
(0x001c) in EncryptedExtensions **unconditionally**, even when the client never
offered it. Chrome, Brave, and Safari do not send `record_size_limit`, so to them
this is an unsolicited extension. RFC 8446 §4.2 requires a client to abort with
`unsupported_extension` on any extension it did not request; BoringSSL and Apple's
stack enforce this and abort mid-handshake, which the browser surfaces as
`ERR_SSL_PROTOCOL_ERROR`. openssl, curl, and a hand-written client all silently
ignore the stray extension, which is exactly why every non-browser client
"worked" and masked the bug. (Go's `crypto/tls` does not implement
`record_size_limit` at all, so it never had this problem.)

**Fix:** `crypto/tls/13/tlsServer.ky` now tracks whether the client offered
`record_size_limit` (`clientSentRecordSizeLimit`) and only echoes it in
EncryptedExtensions when it did. Mirrored to the kyte repo. After rebuilding the
server, the control plane loads cleanly in Chrome/Brave/Safari over TLS 1.3.

Note this bug also affected a production (publicly-trusted) cert — the browser
abort is independent of trust — so the fix is required regardless of certificate.

**Two things were needed for the browser to load:**
1. The `record_size_limit` fix above (the TLS defect).
2. A browser-trusted cert for localhost: an mkcert-issued leaf plus a one-time
   `mkcert -install` so the local CA is in the OS/browser trust store.
